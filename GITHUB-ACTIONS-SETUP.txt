WHAT HAPPENS ON PUSH TO MAIN
-----------------------------
1. GitHub Actions triggers automatically
2. Connects to your server via SSH
3. Switches to quidpath user
4. Pulls latest code
5. Builds new Docker image
6. Rolling update (zero downtime)
7. Runs migrations (backend services only)
8. Collects static files (backend services only)
9. Health check
10. Reports success or failure

HOW TO ADD SECRETS
==================

For Backend Repository (quidpath-backend):
------------------------------------------
1. Go to: https://github.com/YOUR_USERNAME/quidpath-backend/settings/secrets/actions

4. Click "Add secret"
5. Click "New repository secret" again
6. Add SSH_PRIVATE_KEY:
   - Name: SSH_PRIVATE_KEY
   - Value: (paste your SSH private key - see below)

Repeat for:
- Billing: https://github.com/YOUR_USERNAME/billing/settings/secrets/actions
- Tazama: https://github.com/YOUR_USERNAME/tazama-ai-microservice/settings/secrets/actions
- Frontend: https://github.com/YOUR_USERNAME/quidpath-erp-frontend/settings/secrets/actions

HOW TO GET SSH PRIVATE KEY
===========================

Option 1: Use existing key
--------------------------
If you already have an SSH key for the ubuntu user:

On your local machine:
cat ~/.ssh/id_rsa

Copy the ENTIRE output including:
-----BEGIN OPENSSH PRIVATE KEY-----
...
-----END OPENSSH PRIVATE KEY-----

Option 2: Create new key for GitHub Actions
--------------------------------------------
On your local machine:

ssh-keygen -t rsa -b 4096 -C "github-actions" -f ~/.ssh/github_actions_key

Press Enter twice (no passphrase)

Copy the private key:
cat ~/.ssh/github_actions_key

Copy the public key to server:
ssh-copy-id -i ~/.ssh/github_actions_key.pub ubuntu@51.77.147.233

Test connection:
ssh -i ~/.ssh/github_actions_key ubuntu@51.77.147.233

3. Click "Run workflow" button
4. Select "main" branch
5. Click "Run workflow"

TROUBLESHOOTING
===============

Workflow fails with "Permission denied"
---------------------------------------
- Check SSH_PRIVATE_KEY is correct
- Verify key has access to server
- Test: ssh -i ~/.ssh/your_key ubuntu@51.77.147.233

Workflow fails with "Host key verification failed"
---------------------------------------------------
- This is normal for first run
- The workflow will add host key automatically
- Re-run the workflow

Workflow fails with "docker: command not found"
------------------------------------------------
- quidpath user needs docker permissions
- On server run: sudo usermod -aG docker quidpath
- Logout and login: exit, then su - quidpath

Workflow fails with "git pull failed"
--------------------------------------
- Check repository is cloned in correct location
- Should be: ~/quidpath-deployment/backend (or billing, tazama, frontend)
- Clone if missing: cd ~/quidpath-deployment && git clone <repo-url> backend

Health check fails
------------------
- Check service is running: docker ps
- Check logs: docker logs <container-name>
- Verify .env file exists and is correct
- Check port is correct (8000, 8002, 8001, 3000)

ZERO DOWNTIME EXPLAINED
========================

The workflow uses "docker compose up -d --no-deps --build" which:
1. Builds new image
2. Starts new container
3. Waits for new container to be healthy
4. Stops old container
5. Users are seamlessly switched to new container

No downtime! Users don't notice the update.

SUPPORT
=======

If deployment fails:
1. Check Actions tab for error message
2. Review deployment logs
3. SSH to server and check manually
4. Verify .env files are correct
5. Check Docker containers: docker ps
6. Review service logs: docker logs <container-name>

Common issues:
- SSH key incorrect: Re-add SSH_PRIVATE_KEY secret
- Server unreachable: Check SERVER_HOST secret
- Docker permission: Add quidpath to docker group
- Git pull fails: Check repository location
- Health check fails: Check service is running
